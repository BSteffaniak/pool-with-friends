# Mobile browser feasibility record

This record defines the evidence required before PWMTF accepts Bevy as its production browser client. A successful build or desktop smoke test is not acceptance.

## Candidate configuration

- Bevy: `0.19.1`
- Renderer: WebGL2
- Enabled workspace features: `2d`, `ui`, `web`, `webgl2`
- Release profile: optimized, symbols stripped; Binaryen `wasm-opt -Oz` when available
- Browser shell: viewport safe areas, portrait overlay, startup progress, explicit WebGL2/load failure state, and an opt-in feasibility capture panel

Open the built client with `?feasibility` to expose the capture panel. The normal product URL does not show it. Run `./scripts/report-wasm-size.sh` for the exact candidate; both its human-readable table and final machine-readable size evidence come from the same independently verified bundle accounting, and include the build ID, source hash, generated-bundle hash, and Binaryen optimization status injected into reports so bundle measurements cannot be attributed to a different build. Before capture, the tester must identify the platform, hardware model, exact OS/browser family and version, whether this is a proposed-minimum-version run, cache state, presentation tier, and run number; free-text identity fields use trimmed canonical spelling, surrounding whitespace is rejected at both capture and offline validation, and run number is handler-checked as an integer from 1 through 99 rather than trusting native form validity, then serialized with exact numeric conversion rather than permissive integer-prefix parsing. capture refuses a declared platform that differs from user-agent/touch detection, an unknown browser, a declared browser family that differs from user-agent detection, or a declared browser version that differs from the normalized full dotted user-agent version, preventing a known-invalid report from consuming a physical run. The build/release ID, exact source hash, and optimization status are injected by the build and these fields are embedded in the versioned report and its filename. Final-gate validation rejects unoptimized reports, mixed candidate identities, and old report schemas. Before export, every required observable physical check must be recorded as Pass or Fail, including browser-chrome expansion/collapse, and platform-tool measurements for first-visible table, first accepted input, steady/peak memory, thermal status, and reload/eviction must be entered. Parsed-null observations and missing readiness/contact timing fail closed even if native form validity is bypassed; display, interaction-transition, capture-boundary, and marked-event orientation strings must also be present where required, bounded, and control-free in offline evidence; browser-reported screen and viewport dimensions must be positive integers while device-pixel ratio remains positive and finite. Both first-visible table and first accepted input must meet the cold/warm startup budget in final-gate mobile evidence; reaching a visible but non-interactive table does not pass startup. Capture-time and offline validation cross-check operator startup observations against automatic client-ready and first-contact telemetry, rejecting impossible event ordering. Memory observations must be positive measured MiB values at both capture and offline validation; zero is rejected as missing evidence rather than treated as a valid measurement. The panel will not export until the tester explicitly starts and stops a non-zero capture. Capture start and stop both require the page to be foregrounded, preventing a partially hidden interval from being truncated at either boundary. Lifecycle evidence requires exactly two background/foreground, page-hide/show, and orientation cycles; extra transitions contaminate the run and require a restart. The two background intervals must each last at least 30 seconds, and audio suspension/resume evidence is additionally required. Lifecycle export itself enforces the two 30-second minimum intervals before download, and the offline final-matrix validator independently repeats that check. The offline validator also rejects impossible audio lifecycle counters, such as more suspensions than recorded background intervals or more explicit resumes than suspensions. Capture-time export now rejects the same impossible audio lifecycle counter relationships as the offline validator, so known-invalid reports cannot be downloaded. The panel excludes time spent while the document is hidden from capture duration, frame-rate, and frame-gap samples, while lifecycle counters and marked events continue to record background/foreground transitions. Capture-time export enforces the one-minute active interaction duration and ten-minute active lifecycle duration before download, matching offline validation. Capture-time export and offline validation both reject backgrounded interaction captures, requiring a clean restart instead of allowing contaminated performance data to download. Non-lifecycle interaction captures containing orientation changes are also rejected at capture-time export and offline validation, keeping aim/power performance runs in one stable landscape viewport. Capture-time export and offline validation also reject any visibility or page hide/show transitions in interaction runs, closing event-order cases where a background interval might be missing or truncated. Page-cache restoration is likewise treated as lifecycle-only evidence and contaminates an interaction capture. Interaction captures with audio suspension or foreground-resume evidence are rejected as lifecycle-contaminated at both capture-time export and offline validation. Run `./scripts/test-browser-telemetry.js` after capture-sampler changes; it verifies that background suspension time cannot be misreported as a frame stall or near-zero FPS sample. Telemetry interaction, orientation, visibility, page lifecycle, and page-cache counters now advance only during an active capture, preventing pre-capture setup from satisfying export requirements. Audio playback, mute, suspension, and resume evidence counters now advance only during active capture, preventing setup probes from satisfying export requirements. The panel also records browser/display metadata, including both operator-declared and user-agent-detected browser family, startup and first-contact approximations, one-second frame-rate windows, median/95th/99th-percentile/worst animation-frame intervals, interaction/lifecycle counters (including page hide/show and page-cache restoration), operator-marked events, and JavaScript heap data where the browser exposes `performance.memory`. It exports a versioned JSON report for attachment to this record. Downloaded filenames now include the exact canonical browser version and use the same capture timestamp embedded in the JSON report, making artifacts directly attributable without opening them. The offline validator rejects capture timestamps more than five minutes in the future, preventing materially incorrect device clocks from producing misleading dated evidence. Use **Mark event** for short non-sensitive annotations such as orientation changes, background/foreground boundaries, audio checks, visible throttling, or thermal warnings; never enter identity, credentials, tokens, or unrelated browser data.

The panel also provides a generated Web Audio probe. It creates the audio context only from the probe button's user gesture, supports mute/unmute, deliberately suspends a running probe when the document becomes hidden, and requires a subsequent explicit button gesture to resume. The generated tone is measurement instrumentation, not shipped game audio.

The prototype deliberately contains presentation and input only. It does not establish canonical physics, gameplay authority, networking, or production asset choices.

## Interaction and lifecycle checks

Run every check on each physical mobile class:

- [ ] First load and warm-cache load both reach the table without a blank canvas.
- [ ] Aiming starts only while the pointer or one stable touch contact is held.
- [ ] Dragging in the table area rotates the cue continuously without jumps.
- [ ] Dragging in the right-side power area changes power and remains bounded.
- [ ] Releasing and beginning a new touch does not inherit stale contact state.
- [ ] Resizing preserves the full table at narrow and wide landscape ratios.
- [ ] Browser chrome expansion/collapse does not hide controls.
- [ ] Notches, rounded corners, and home indicators do not cover the canvas content.
- [ ] Portrait orientation covers the game with the rotate notice.
- [ ] Returning to landscape restores the table without a reload.
- [ ] Backgrounding and foregrounding restores rendering and input.
- [ ] The audio probe starts only from its button gesture, mute/unmute is immediate, hiding the page suspends a running context, and returning requires the explicit resume button.

Event markers are accepted only during a visible active capture with finite elapsed time, a known orientation, and a control-free label; offline validation enforces the same visible/non-null contract, so malformed marker evidence fails before mutating the report and if a report is manually altered. The capture report permits an unavailable instantaneous `current_fps` sample as `null`, but validates any supplied value as finite and non-negative; frame count must be a positive integer, and final acceptance continues to use the complete one-second minimum/median/maximum samples rather than that display-only instant. The current prototype has no shipped audio content. Non-lifecycle interaction captures require exactly zero suspension and resume counters. Lifecycle runs require exactly two successful suspensions and two explicit resumes, matching both required background intervals one-for-one. A browser-reported `interrupted` audio context is treated as suspended lifecycle state, which is required for WebKit implementations that interrupt audio while backgrounding instead of exposing only `suspended`. Export requires the final context state to be `running`, matching offline acceptance and preventing a known-invalid stopped or interrupted report from downloading. If interruption occurs after capture stops, the audio control offers a resume-for-export action that does not play another probe or mutate completed evidence counters; capture stop refreshes this state synchronously, gives recovery guidance, and keeps download disabled until recovery succeeds and whenever a transition failure exists. Accepted runs must end unmuted after exactly one mute/unmute cycle; extra cycles are rejected rather than treated as equivalent evidence. Accepted runs contain exactly two probe plays—one audible and one muted—and the probe control disables after both are recorded. Mute controls are enabled only during an active capture with idle audio, preventing uncounted setup or post-stop state changes. Probe playback is enabled only during capture, except for an explicit recovery retry after a recorded transition failure. A new capture cannot begin with a pre-existing suspended audio context; it must be explicitly resumed first. Every new run then requires an explicit reset that closes/discards any existing audio context, so prior-run state cannot leak into later evidence. Audio-context close failures during reset are surfaced and recorded rather than silently ignored. Reset close remains an explicit in-flight lifecycle operation, so another run cannot start until the old context settles. Its opt-in generated-tone probe makes audio lifecycle testing possible without adding a production audio asset; probe, user resume, and visibility-triggered suspend transitions share one serialized queue, verify actual context state before advancing evidence counters, and expose actionable retry status on browser API failures. Transitions re-check page visibility and context state when they actually execute, so a queued resume cannot restart audio after the page becomes hidden. Capture start, stop, report export, and form reset are blocked until any button-driven or visibility-triggered audio transition finishes, so setup/operator activity cannot enter a new evidence window or mutate controls across the recorded boundary. Event markers require an explicitly started, metadata-validated capture and can no longer begin a run implicitly. Event marking is also disabled while audio lifecycle work is pending, preventing marker timestamps from racing transition completion. One shared actionable guard enforces these boundaries consistently. Capture controls mirror their handler guards: marker, reset, and download buttons are enabled only when their evidence boundary is valid. Control states refresh directly at capture start, stop, clear, and audio-transition boundaries rather than depending on a later browser audio event. The panel remains minimized throughout active capture and pending audio transitions, preventing control exposure from changing the test interaction surface. Reports preserve an audio-transition failure count; any failed resume or suspend invalidates capture-time export and offline validation instead of being erased by a later retry. Unsupported audio telemetry must contain no playback, mute, lifecycle, or failure evidence; unsupported browsers initialize audio state as `unsupported` rather than emitting an internally inconsistent `not started` report, and supported launch browsers still must prove the complete audio path. Failures before capture also block a new run until the operator explicitly resets the form, so setup failures cannot be silently discarded. Audio lifecycle remains open until the behavior above is measured on iOS Safari and Android Chrome.

## Measurement procedure

Use an uncached production build served over HTTPS or a representative throttled local connection. Capture at least three runs per device and report the median plus the worst observed run.

1. Run `./scripts/report-wasm-size.sh` and copy the raw and gzip totals into this record. The build writes and immediately verifies a manifest that binds the candidate identity to the SHA-256 and byte size of every expected generated asset; its versioned length-prefixed bundle-hash algorithm also binds captures directly to the finalized generated assets. The size reporter and physical HTTPS server verify that manifest before reusing `dist/`, so missing, unexpected, symlinked, or modified files fail closed. The manifest itself is build metadata and is excluded from transfer totals and from the server's public asset allowlist. The server loads only manifest-approved assets, refuses filesystem traversal and unknown paths, returns explicit JavaScript/WASM types, and applies a same-origin content-security policy with no external dependencies. The size reporter independently fails closed unless the build ID contains the source hash and the measured candidate is `wasm-opt-Oz`; unoptimized reporting requires an explicit troubleshooting-only override. The local HTTPS serving path also fails closed on unoptimized or source-unbound bundles, including when reusing `dist/`. The local HTTPS server verifies that its certificate covers the declared public host before listening; this supplements, but cannot automate, device trust verification. It also rejects invalid, near-expiry, shared-file, or certificate/key-mismatch inputs before serving. The `./scripts/test-feasibility-server.sh` self-test exercises host/key rejection plus optimized TLS startup and security headers. The script also reports Brotli sizes when the `brotli` executable is available.
2. Build and serve `dist/` over HTTPS, then open `/?feasibility` for the default tier or `/?feasibility&tier=reduced` for a required fallback measurement. Enter the exact device/browser metadata and run number, then start a fresh capture after the table is visible. The tier is URL-bound, displayed by the Rust client, and exported automatically rather than accepted as a tester assertion. `./scripts/serve-feasibility.sh` provides a local-network HTTPS server when given a device-trusted certificate; its exact environment variables are documented in `packages/client/README.md`. A self-signed certificate that the device does not trust is not representative evidence.
3. Record navigation start to first visible table and navigation start to first accepted input. The exported report supplies client-ready and first-contact approximations; use browser tooling for the final visible-paint measurement.
4. Record steady-state memory after 60 seconds and peak memory during load using platform tooling. Treat the JSON JavaScript heap figures as supporting evidence only because Safari and Firefox may not expose them and they exclude WASM/graphics memory.
5. Capture one minute of repeated aim and power interaction and report median, 95th-percentile, 99th-percentile, and worst frame time. The panel exports those animation-frame interval summaries plus one-second FPS windows as supporting evidence, not a replacement for browser/platform traces.
6. Keep the app active for 10 minutes, including repeated orientation changes and at least two 30-second background/foreground cycles.
7. Exercise the audio probe before and after mute, background the page while its context is running, then explicitly resume from the button after foregrounding.
8. Record every physical check in the panel as Pass or Fail. Enter first-visible/accepted-input timings and steady/peak memory from browser/platform tooling, plus thermal and reload/eviction results. Use **Mark event** at lifecycle and observable thermal boundaries, then download the JSON report and note any graphics reset, audio failure, or input loss. Keep labels short and free of identity or secret data.
9. After at least three runs for each comparable device/browser/cache-state group, put the report JSON files in local `feasibility-reports/` and run `./scripts/validate-feasibility-matrix.sh`. The wrapper holds the generated-bundle process lock for its complete transaction, so accepted-candidate verification, report validation, size evidence, and decision publication cannot race a concurrent build. A passing complete matrix writes `feasibility-reports/acceptance-decision.md` and `wasm-size-evidence.json` with the exact accepted candidate, a deterministic hash of the complete canonical report set, per-asset raw/gzip sizes, totals, and minimum browser versions; a failure writes neither artifact, and existing evidence is never overwritten implicitly. Override `PWMTF_FEASIBILITY_REPORTS` or `PWMTF_FEASIBILITY_BUNDLE` only when the report or verified bundle directories are elsewhere. The expected-bundle check is mandatory in final-matrix mode, independently verifies the complete generated bundle even when the summarizer is invoked directly, and binds every report back to the verified candidate instead of trusting report-internal or manifest-only identity fields. The final wrapper independently verifies the complete bundle before reading reports, so even a well-formed manifest with tampered generated assets cannot become acceptance evidence. It rejects malformed reports, missing or unknown required checks, duplicate run numbers, groups with fewer than three runs, or final evidence collected across more than 30 days, then prints a Markdown median/worst table for this record. For final mobile-gate evidence, add `--require-mobile-matrix`; it also rejects missing platform/cache groups or proposed-minimum-version evidence for any mobile class, failed physical checks, either first-visible or first-accepted-input startup budget failures, captures shorter than the required one or ten minutes, unavailable FPS/frame-time summaries, FPS below 30, an unproven 30–55 FPS fallback, thermal/reload failures, missing background/orientation cycles, and incomplete pre/post-mute or suspend/resume audio evidence. `./scripts/test-feasibility-tools.sh` self-tests a complete synthetic matrix and representative matrix/minimum-version, FPS, startup-budget, interaction/lifecycle-duration, and audio-lifecycle rejection paths. Use `--allow-incomplete` only for interim troubleshooting; it cannot be combined with final-gate mode.
10. Repeat on the quality fallback if the default tier cannot hold the target frame rate.
11. Save screenshots or traces with this record's date/device labels; do not store user credentials or unrelated browser data. The default local `feasibility-reports/` directory and downloaded `pwmtf-feasibility-*.json`, `*.trace`, and `*.har` evidence are ignored by Git and should remain local unless deliberately sanitized and approved for publication.

## Quality fallback

If a supported device cannot sustain 55 FPS during the one-minute interaction capture but remains at or above 30 FPS, repeat the matrix with `tier=reduced`. The reduced-tier URL currently proves fallback selection/reporting; this sparse feasibility scene has no nonessential effects to remove. Before Phase 8, any device requiring reduced mode must receive concrete reductions to decorative effects, resolution scale, animation density, or nonessential audio voices without changing canonical simulation, input quantization, table geometry, or rules. A device below 30 FPS, one that repeatedly reloads from memory pressure, or one that cannot reliably restore after foregrounding fails this gate.

## Acceptance decision

**Status: pending physical-device evidence.**

The measurement-budget table references the latest locally measured optimized candidate rather than stale bundle totals, keeping the decision summary and acceptance record internally consistent. The 2026-08-20 local release build for source `740cbd0ca5e1e1e5df9937c444302d29626b1ae07efd0a8373a042649fb8c60e` produced a 26,979,931-byte `wasm-opt -Oz` WASM file (8,095,578 bytes with gzip). The complete generated bundle is 27,151,980 bytes raw and 8,125,178 bytes when each asset is gzip-compressed. Reports use schema version 11 and preserve final orientation in addition to initial and ordered transition states; both capture-time and offline validation prove the run actually stopped in landscape. Capture-time export enforces the same exact sequence and final state as offline validation, preventing known-invalid orientation runs from downloading. Final lifecycle validation still requires exactly two orientation changes—portrait, then landscape—after an initial landscape state, eliminating ambiguous extra rotation events. Reports also preserve visible capture-boundary assertions; offline validation rejects reports not started and stopped in the foreground. Reports bind detected platform, declared/detected browser versions, hidden-interval durations, and optimization status alongside the build ID and source hash. The offline validator requires the build ID itself to contain the full source hash, preventing independently edited build/source fields from masquerading as a bound candidate identity. Final-matrix validation rejects old schemas, unoptimized or mixed candidates, overlapping current/minimum browser versions, inconsistent hardware within a mobile platform class, and missing browser-chrome checks. Lifecycle captures are explicitly exempt from cold/warm startup budgets while retaining their ten-minute and lifecycle checks. The capture sampler resets its active frame window across visibility transitions, so time spent suspended in the background cannot falsely fail frame-gap or minimum-FPS budgets; a focused Node self-test covers this behavior. The automated Google Chrome 151.0.7922.169, Microsoft Edge 151.0.4129.93, and Firefox 152.0.4 smoke tests on macOS 26.6.1 (MacBook Air, Apple M4) load normal, default-feasibility, and reduced-feasibility entry points at 1280×720, reach the ready canvas, find the required capture controls, and verify reduced-tier reporting. Safari automation remains blocked until the user-controlled **Allow remote automation** setting is enabled. Desktop smoke skips the slow Binaryen post-pass but still uses the release Rust/WASM build; the recorded size and all physical acceptance runs use the optimized bundle. Desktop smoke is not mobile compatibility or performance evidence.

Bevy is accepted only after every required mobile row passes the interaction/lifecycle checks, measured results meet the budget or the defined quality fallback, exact minimum browser versions are recorded, and audio lifecycle is proven. Otherwise record the failing evidence and reject or revise the client direction before introducing dependent client architecture.
