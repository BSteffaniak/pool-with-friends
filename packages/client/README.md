# PWMTF browser client

This package owns the Bevy/WASM presentation feasibility prototype. It intentionally contains no canonical pool physics or rules.

## Native check

```sh
cargo run -p pwmtf_client
```

## Web build

```sh
./scripts/build-wasm.sh
./scripts/serve-wasm-bundle.py --port 8080 --directory dist
```

Open `http://localhost:8080`. Do not replace the verified server with an unrestricted directory server: it validates the generated manifest and bundle identity before listening and exposes only approved assets with the same response policy used by browser smoke tests and physical HTTPS capture. The release bundle uses Bevy's WebGL2 renderer for broad modern-mobile-browser compatibility. Each build removes every stale top-level file, directory, or symlink from `dist/` before generating the complete bundle, computes a deterministic, versioned length-prefixed SHA-256 identity of the finalized generated assets and injects it into the capture client, then writes and verifies `pwmtf-bundle-manifest.json` with that candidate identity and SHA-256/size of every expected asset. The manifest is not counted as a shipped asset in size totals. The physical HTTPS server and size reporter verify this manifest before using an existing bundle, so incomplete, unexpected, symlinked, or modified assets fail closed and size reports and served assets describe only the current build. The build always injects a deterministic SHA-256 of the explicit Cargo, toolchain, client, Nix, WASM build, verification, locking, serving, measurement, and final-validation inputs that can alter generated bytes or candidate-evidence semantics. Run `./scripts/hash-wasm-source.py --list-inputs` to inspect this fail-closed inventory. The build uses `PWMTF_BUILD_ID` when supplied; otherwise it derives the build ID from the Git revision plus that source hash, so explicit release labels remain independently tied to exact candidate inputs and reports from changed working-tree candidates cannot be silently combined. When Binaryen is available, the build script applies size-oriented WebAssembly optimization. Desktop smoke scripts set `PWMTF_SKIP_WASM_OPT=1` to avoid repeating the slow Binaryen pass; physical measurements, bundle reports, and acceptance builds must not set it.

The selected presentation tier is URL-bound rather than self-reported: use `?feasibility` for default quality or `?feasibility&tier=reduced` for the reduced fallback, and the client displays/exports the active tier. The panel requires exact device/browser, candidate build ID, source hash, generated-bundle hash and algorithm, proposed-minimum-version, cache-state, presentation-tier, and run metadata plus Pass/Fail results and platform-tool timing/memory/thermal/reload observations before export. It captures frame-rate windows, median/95th/99th-percentile/worst frame intervals, lifecycle counters, non-sensitive operator-marked events, available JavaScript heap data, and a versioned JSON report with a device/run-specific filename. After collecting at least three comparable runs, place them in `feasibility-reports/` and run `./scripts/validate-feasibility-matrix.sh`; the wrapper holds the generated-bundle process lock for its complete transaction, independently verifies `dist/`, always enables final-matrix validation against it, requires the complete evidence set to fit within a 30-day capture window, and writes explicit acceptance and machine-readable candidate-bound size evidence only after every gate passes; the acceptance decision includes a deterministic hash of the complete canonical report set, and the wrapper refuses to overwrite existing evidence without explicit removal. `./scripts/test-feasibility-matrix-lock.sh` deliberately overlaps final validation with a rebuild and proves rejected evidence observes one complete candidate and publishes neither final artifact. Machine-readable size evidence independently re-verifies the entire bundle and is deterministic for identical inputs; `./scripts/test-wasm-size-evidence.sh` covers repeatability, totals, candidate binding, and tamper rejection. Set `PWMTF_FEASIBILITY_REPORTS` or `PWMTF_FEASIBILITY_BUNDLE` only for alternate directories. Add `--require-mobile-matrix` for final browser-gate evidence; final mode requires `--expected-bundle dist`, then requires cold, warm, and lifecycle runs at both current and proposed-minimum versions for iPhone Safari, iPad Safari, Android phone Chrome/Firefox/Samsung Internet, Android tablet Chrome, and desktop Safari/Chrome/Firefox/Edge, and fails closed on mixed candidate identities, missing browser/version/cache groups, physical/budget/FPS/frame-time/duration/lifecycle/audio failures (including pre/post-mute playback), or an unproven quality fallback. Run `./scripts/test-feasibility-tools.sh` to self-test a complete passing synthetic matrix plus matrix/minimum-version, FPS, startup-budget, interaction/lifecycle-duration, and audio-lifecycle rejection paths. Downloaded feasibility JSON, trace, and HAR evidence is ignored by Git by default; keep it local unless deliberately sanitized and approved. These are measurement support only; final acceptance still requires the physical-device and platform-tooling evidence in `docs/mobile-feasibility.md`.

## Feasibility validation

The prototype now includes an opt-in `?feasibility` capture panel and generated audio-lifecycle probe for collecting physical-device evidence. Use `./scripts/report-wasm-size.sh` for a reproducible human-readable raw/gzip bundle report derived from the same independently verified machine-readable evidence used by final validation; it prints the candidate build, source, bundle identity, and algorithm before per-asset totals. Set `PWMTF_SKIP_BUILD=1` only to inspect an existing identified `dist/` candidate without rebuilding, then follow `docs/mobile-feasibility.md` for the required browser/device matrix, interaction checks, performance capture procedure, fallback threshold, and acceptance record. The checked-in Chromium smoke test validates both the normal generated shell and the opt-in feasibility entry point, asserts the capture controls are present, and prints the exact browser version used:

```sh
./scripts/test-browser-smoke.sh
```

On macOS, Safari compatibility has a matching WebDriver smoke entry point. First enable **Allow remote automation** in Safari's Developer settings, then run:

```sh
./scripts/test-safari-smoke.sh
```

Firefox has an equivalent headless WebDriver check for normal, default-feasibility, and reduced-feasibility entry points. It also verifies required capture controls and reduced-tier reporting:

```sh
FIREFOX_BIN=/path/to/firefox \
GECKODRIVER_BIN=/path/to/geckodriver \
./scripts/test-firefox-smoke.sh
```

Safari exercises the same three entry points and feasibility assertions. Neither desktop smoke substitutes for the physical mobile matrix.

## Physical-device HTTPS serving

Mobile feasibility must be measured in a secure context using a certificate the device trusts. Prepare a certificate and key whose subject covers a hostname or IP reachable from the test devices, then run:

```sh
PWMTF_FEASIBILITY_HOST=pool-test.example.test \
PWMTF_TLS_CERT=/absolute/path/to/certificate.pem \
PWMTF_TLS_KEY=/absolute/path/to/private-key.pem \
./scripts/serve-feasibility.sh
```

Optional `PWMTF_FEASIBILITY_BIND` and `PWMTF_FEASIBILITY_PORT` values select the listener; the defaults are `0.0.0.0` and `8443`. Set `PWMTF_SKIP_BUILD=1` only to reuse an existing `dist/` build. The HTTPS physical-device server independently refuses unoptimized or source-unbound bundles before listening, so `PWMTF_SKIP_BUILD=1` cannot accidentally serve desktop-smoke artifacts as physical evidence. Open the printed `https://…/?feasibility` URL on each test device. The server verifies that the certificate covers `PWMTF_FEASIBILITY_HOST` before listening; device trust still must be established externally and warnings must never be bypassed. The server also rejects invalid, near-expiry, shared-file, or certificate/key-mismatch TLS inputs before serving. Listener ports are validated before certificate/build work begins, producing a bounded actionable error for malformed configuration. TLS is constrained to version 1.2 or newer, listener reuse is disabled, and request threads cannot delay shutdown. The local test server uses a bounded accept queue and timeout in addition to daemon request threads, avoiding unbounded pending connection growth during physical testing. The `./scripts/test-feasibility-server.sh` self-test covers certificate-host mismatch, key mismatch, optimized server startup, and required response security headers. CI explicitly verifies that its pinned runner image provides OpenSSL and curl, while the Nix shell declares both dependencies; CI does not mutate runner packages during validation. The server self-test rebuilds automatically when `dist/` is missing or unoptimized, so CI and local validation do not depend on prior command ordering. It also proves that rebuilding removes stale nested `dist/` artifacts before restoring the optimized physical candidate. The build and every script or Python entry point that builds, serves, verifies, measures, or validates the shared `dist/` candidate take the same process lock under `target/`, preventing both high-level commands and direct lower-level invocations from replacing or observing the bundle during another operation. `./scripts/test-wasm-bundle-lock.py` proves same-process nesting, subprocess inheritance, environment restoration, and independent-process exclusion; `./scripts/test-wasm-bundle-concurrency.sh` then exercises a build, Chrome and Edge browser smoke tests, the final-matrix tool test, and bundle-integrity validation concurrently and proves they complete without mixed-candidate failures. Chromium-family smoke tests use the same explicit SwiftShader/ANGLE flags, avoiding Edge's intermittent native headless GPU mailbox failures while still exercising WebGL2. `./scripts/test-wasm-bundle-integrity.sh` independently proves that the generated manifest rejects modified, missing, unexpected, symlinked, or candidate-mismatched bundle contents. The HTTPS server serves only the manifest-approved in-memory asset set, never exposes the manifest or filesystem paths, returns explicit JavaScript/WASM content types and lengths, and applies a same-origin content-security policy plus opener/resource isolation and the documented security headers. Browser smoke tests use this same allowlisted HTTP server implementation without TLS, so automated compatibility checks exercise the production-like response policy rather than Python's unrestricted directory server. `./scripts/test-browser-smoke.sh` and `./scripts/test-edge-smoke.sh` cover Chromium and Edge normal/default/reduced entry points; Firefox and Safari have equivalent WebDriver scripts. `./scripts/test-wasm-bundle-server.sh` covers malformed configuration, tamper rejection, allowlisted HTTP responses, security headers, and manifest non-disclosure; `./scripts/test-wasm-reproducible-build.sh` proves identical source inputs and an explicit build ID produce byte-identical generated bundles both before and after the required Binaryen `-Oz` pass. CI runs both after the release build. The server self-test covers all of those response boundaries, near-expiry certificate rejection, malformed and out-of-range listener ports, DNS and IP subject-alternative-name certificates, and rebuilds from a completely missing `dist/` bundle as documented. Do not expose the private key.
